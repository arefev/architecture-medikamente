# Cutover-план миграции информационной системы

## 1. Обоснование выбора стратегии миграции

**Выбранная стратегия: Branch by Abstraction**

### Почему именно она

| Критерий                                    | Обоснование                                                                                                                                                                             |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Наличие монолита с высокой связанностью** | В монолите сложно выделить отдельные модули для параллельного запуска. Branch by Abstraction позволяет скрыть детали реализации за абстракциями и переносить функциональность по слоям. |
| **Требуется минимизация рисков простоя**    | Система продолжает работать без остановки, так как старый и новый код сосуществуют.                                                                                                     |
| **Неоднородность бизнес-логики**            | Удобно переносить по частям: сначала слой данных, затем доменная логика, затем API.                                                                                                     |
| **Сложная интеграция с внешними системами** | Абстракции позволяют адаптировать интерфейсы, не нарушая работу текущих интеграций.                                                                                                     |
| **Ограниченные ресурсы команды**            | Нет необходимости поддерживать полный parallel run — только совместимость слоёв.                                                                                                        |

### Ограничения

* Увеличивается сложность кода на время миграции.
* Нужно строгий контроль версий интерфейсов.
* Требуется единая архитектурная дисциплина.

## 2. Cutover-план миграции

| Этап                                                    | Описание действия                                                                  | Ключевые задачи                                                          | Ответственные                   | Сроки      | Риски                                      | Меры снижения                              |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------- | ---------- | ------------------------------------------ | ------------------------------------------ |
| **1. Анализ и подготовка**                              | Оценка текущего монолита, определение границ абстракций                            | Выделение доменных модулей; выявление зависимостей; документирование API | Архитектор, системный аналитик  | 1–2 недели | Неправильные границы модулей               | Провести воркшопы, ревью архитектуры       |
| **2. Создание уровня абстракций (Abstraction Layer)**   | Создание интерфейсов, через которые монолит начинает обращаться к функциональности | Определить интерфейсы; разработать адаптеры; написать тесты              | Архитектор, ведущий разработчик | 1 неделя   | Ошибки в дизайне интерфейсов               | Архитектурное ревью, интеграционные тесты  |
| **3. Интеграция абстракций в монолит**                  | Подключение слоя абстракций без изменения поведения                                | Рефакторинг монолита, перевод вызовов на абстракции                      | Команда разработки              | 2 недели   | Нарушение работы монолита                  | Canary-тесты, мониторинг логов             |
| **4. Реализация новой функциональности в микросервисе** | Создание микросервиса, повторяющего логику монолита                                | Разработка; CI/CD; настройка БД; конфигурация транспорта                 | Разработчики сервисов, DevOps   | 2–4 недели | Неконсистентность данных                   | Синхронизация данных, миграционные скрипты |
| **5. Переключение абстракции на новый сервис**          | Abstraction Layer начинает вызывать новый микросервис                              | Настройка маршрутизации; обновление адаптеров; тестирование              | DevOps, разработчики            | 1 неделя   | Повышенная нагрузка, ошибки ответа сервиса | Blue-Green или Canary Deployment           |
| **6. Тестирование после переключения**                  | Проверка корректной работы всего функционала                                       | Интеграционные тесты; нагрузочное тестирование                           | QA-инженеры                     | 1–2 недели | Не выявлены скрытые дефекты                | A/B тесты, расширенный мониторинг          |
| **7. Отключение старой логики монолита**                | Удаление старой реализации                                                         | Чистка кода; отключение старых модулей                                   | Техлид + Backend                | 3–5 дней   | Отключение нужной логики                   | Code review и автоматические тесты         |
| **8. Завершение миграции и стабилизация**               | Документирование, мониторинг, обучение сотрудников                                 | Мониторинг SLA; исправление ошибок                                       | Вся команда                     | 2 недели   | Деградация производительности              | Автоматическое оповещение, SRE-контроль    |

## 3. Критические моменты и меры по снижению рисков

### Критические точки

1. **Создание и правильное проектирование Abstraction Layer**
   Неправильные интерфейсы → дублирование логики → ошибки.

2. **Согласованность версий API и контрактов**
   При изменениях легко нарушить совместимость.

3. **Синхронизация данных между монолитом и микросервисом**
   Может возникнуть состояние гонки при миграции.

4. **Нагрузка на инфраструктуру при включении нового сервиса**
   Возможны всплески нагрузки.

### Меры

| Риск                            | Митигирующие меры                              |
| ------------------------------- | ---------------------------------------------- |
| Несоответствие интерфейсов      | Контрактные тесты, API-first                   |
| Ошибки в критичной логике       | Canary-релизы, фича-флаги                      |
| Утечка данных/неконсистентность | Двунаправленная синхронизация, транзакции в БД |
| Сбой при переключении трафика   | Blue-Green Deployment                          |
| Дефицит компетенций команды     | Обучение, pair-programming                     |
| Длительное время миграции       | Автоматизация CI/CD, инкрементные релизы       |

## 4. Распределение ролей

| Роль              | Ответственности                                      |
| ----------------- | ---------------------------------------------------- |
| **Архитектор**    | Определение слоёв абстракции, ревью интерфейсов      |
| **Техлид**        | Руководство разработкой, контроль совместимости кода |
| **Разработчики**  | Реализация адаптеров, миграция логики                |
| **DevOps/SRE**    | CI/CD, переключение трафика, мониторинг              |
| **QA**            | Интеграционное и нагрузочное тестирование            |
| **Аналитики**     | Актуализация требований, документирование            |
| **Product Owner** | Приоритизация, управление рисками бизнеса            |
